# POLYROB Configuration Reference (env flags SSOT)

This is the single source of truth for POLYROB's environment/config flags. Every default
below is **read from source** (the `os.getenv`/`_bool_env` default or the `BotConfig`
`Field(default=...)`), not from prose, and a contract test fails when a flag read in the
code has no row here or a row names a flag the code no longer reads. `polyrob doctor --flags`
prints the same table with the values resolved on your box. When reasoning about a default,
**cite the code anchor and re-check it** — lines rot, so anchors are `file.py:line` but trust
the *group/symbol* over the exact number. The user guide that explains these settings is
[`guide/configuration.md`](guide/configuration.md). Boolean defaults follow POLYROB's falsey-set
semantics: a flag read via `_bool_env(name, default)` (`agents/task/constants.py:194`)
returns `default` when unset/blank, else `True` unless the value is one of
`{none, off, false, 0, no}`.

---

## Env files & layering (which file configures what)

The candidate list + precedence order is the SSOT `core.paths.env_file_candidates`;
`polyrob config path` prints the live view, and `polyrob doctor` names the source tier on
every credential line.

**Local/CLI mode** (`POLYROB_LOCAL`; loaded first-wins, `override=False`, so process env
beats every file): process env > `./.polyrob/.env` (project — `polyrob config set`) >
`~/.polyrob/.env` (global — `polyrob config set --global`, `polyrob auth add`) > legacy
`~/.rob/.env` (read-only fallback) > root `.env` > `config/.env.{env}` >
`config/.env.{env}.local`.

**Server mode** (loaded reversed with `override=True`, so files win and
`config/.env.{env}.local` is the top file layer): `config/.env.{env}.local` >
`config/.env.{env}` > root `.env`.

**What `config/.env.*` remains FOR:** the server-mode **non-systemd** deploy only (the OSS
self-hosting posture — `polyrob serve` / `python main.py` on a box with no unit-file env).
A systemd deploy gets its env from `/etc/polyrob/polyrob.env` via the unit file and never
reads the repo `config/` files. On a dev checkout the CLI keeps `config/.env.*` only as
the LOWEST back-compat layers; CLI keys belong in `~/.polyrob/.env` — copy them once with
`polyrob config migrate` (the automatic backfill is retired; see
`POLYROB_ENV_KEY_BACKFILL`).

**Environment names:** there are exactly two meaningful names, `development` (default)
and `production` — there is **no staging environment**. The name resolves
`CONFIG_ENV` > `ENV` > `development` (`core/bootstrap.py::load_env`; `api/server_boot.py`
delegates there too). Two separate deployment-mode vars still exist with their own
semantics: `ENVIRONMENT` (api auth cookie gates, defaults `production`) and `POLYROB_ENV`
(MCP encryption gate, defaults `development`, falls back to `ENVIRONMENT`) — unifying the
four names into one var is a tracked follow-up (2026-08-14 env-scheme investigation).

The aux-model slot set is intentionally fixed at 3 (`compaction`/`judge`/`reflection`) —
the real aux LLM call sites in the codebase. A dead `planner`/`vision` slot pair with zero
call sites was removed; extend the slot set only when a new aux-consuming feature actually
lands, not speculatively.

Per-provider **API keys / base URLs** are `BotConfig` fields (default `None`/SDK
default): `OPENAI_API_KEY`, `ANTHROPIC_API_KEY`, `GEMINI_API_KEY`, `DEEPSEEK_API_KEY`,
`DEEPSEEK_API_URL` (`https://api.deepseek.com/v1`), `OPENROUTER_API_KEY`,
`NVIDIA_API_KEY`, `NVIDIA_API_URL` (`https://integrate.api.nvidia.com/v1`),
`PERPLEXITY_API_KEY` — see `core/config.py:54-65`.

**Default provider preference** (2026-06-24). When no provider is given explicitly
(`-p`/`SessionRequest.provider`) or pinned (`DEFAULT_PROVIDER`/`CHAT_PROVIDER`), the
default is the first provider **with a key present**, in `modules/llm/profiles.py`
`PROFILES` order: **`openrouter` → `anthropic` → `openai` → `gemini` → `nvidia` →
`deepseek`**. OpenRouter is first, so a host with an `OPENROUTER_API_KEY` defaults to
OpenRouter even when other provider keys are also present. To force a different
default, set `DEFAULT_PROVIDER=<provider>` or pass `-p`.

**Per-provider default-model override** — `POLYROB_<PROVIDER>_MODEL` (e.g.
`POLYROB_OPENROUTER_MODEL=x-ai/grok-4.3`; unset by default) overrides the hardcoded
`DEFAULT_MODELS` entry for that provider, so a headless deploy can pin/swap the model
with an env change + restart, no code change — see
`modules/llm/llm_client_registry.py::get_default_model`. A hyphenated provider name
(`zai-coding`) maps to underscores in the env name (`POLYROB_ZAI_CODING_MODEL`);
alternatively set the row's own `default_model:` in `providers.yaml`.

## Autonomy & continuous-learning loops

All read through `AutonomyConfig` (`agents/task/constants.py:250+`). The local profile
now has TWO buckets under `POLYROB_LOCAL`: the **interactive** tools a user drives
(coding, git, knowledge base, memory/RAG, project-context, messaging, prefs) flip ON as
a group, but the self-directed **autonomy** loops (self-wake, goal board + planner,
curator, background-review, episodic continuity, self-writing) default OFF for a new
install and require `AUTONOMY_ENABLED` (see below). An explicit per-flag env always wins.

**`AUTONOMY_ENABLED`** is the single owner-legible master switch for the local autonomy
loop group. Default OFF for a new local install (so `polyrob run`/REPL is interactive-only
until you opt in); ON automatically when you set an autonomous posture/mode
(`AUTONOMY_MODE=autonomous` effective, or `AUTONOMY_POSTURE` owner-visible/full), so a
deliberate autonomy choice is never left inert. Multi-tenant server behavior is unchanged
(local off ⇒ the whole autonomy group off regardless):

| `AUTONOMY_ENABLED` | Default | What it does | Code anchor |
|---|---|---|---|

## Preferences (owner UX)

The console appearance preference `ui.theme` accepts `auto` (default), `dark`, or
`light`. Change it in Agent → Settings; it applies immediately through the existing
preferences writer. `auto` follows the browser's system preference. Public/login
pages follow the system without loading owner preferences. Anchors:
`core/prefs.py::PREF_SCHEMA`, `webview/theme.py::theme_preference`.

`core/prefs.py` module docstring for the full schema/merge contract.

> last row). With every money flag OFF, no money code ever *executes* and no money value can ever
> *move* — but four things are present on disk/wire regardless of flag state:
> 1. The empty `x402_payment_requests` and `subscriptions` tables are always created at DB init
>    (`modules/database/database_manager.py:83-84`), never populated while their flags are off.
> 2. `GET /api/x402/*` (info-only route, self-labels `payments {'enabled'/'info-only'}`) is always
>    mounted (`api/app.py`, "always register — endpoints self-check if x402 is configured").
> 3. `/eip8004/registration.json` + the reputation/validation reads are always mounted and served
>    (`api/app.py`), reporting `trustMode: "local"` and empty reputation when `EIP8004_ENABLED` is
>    off — a read, not a write.
> 4. `/api/payments/*` is always mounted (`api/app.py`); each handler self-checks
>    `container.get_service('balance_manager')` at request time and 404s/503s when `ENABLE_AUTH` is
>    off, rather than being absent from the route table.
>
> None of the four can move value or register a service — the "no money code runs" guarantee holds
> — but a port scan / route enumeration will see these paths respond even on a deployment that has
> enabled nothing. Treat "byte-identical" as "functionally inert," not "the process looks identical
> on the wire."

### Posture ↔ billing (C9)

Own-ops deployments (Posture 0 `local`, Posture 1 `own_ops` — see `webview/webgate.py::posture()`)
run with **no billing services registered** by default. The gate is `ENABLE_AUTH` (`BotConfig.enable_auth`,
default OFF): `core/initialization.py::initialize_auth_services()` — called unconditionally from
`core/bot.py` on every boot — checks `container.config.enable_auth` first and returns immediately
when it's `False`, *before* it ever reaches the code that would register `balance_manager`,
`tier_manager`, `api_key_manager`, `wallet_generator`, or the deposit monitor. `X402_ENABLED`
(default OFF) independently gates `X402PaymentMiddleware` — it's only added to the app when true
(`api/app.py`). Own-ops instances authenticate solely via the owner's own LLM provider API keys —
there is no metered usage to bill.

> **Correction vs. the original C9 plan:** the plan assumed `ENABLE_CREDIT_SYSTEM`
> (`BotConfig.enable_credit_system`) was the off-by-default gate. It isn't — it has defaulted
> `True` since 2025-11-13 (commit `72cf279d`), predating Workstream C entirely, and is only ever
> consulted *inside* `initialize_auth_services()`, after the `enable_auth` check — so it's inert
> whenever `ENABLE_AUTH` is off (the default). It is not a regression; the plan simply misidentified
> which flag does the gating. `tests/unit/api/test_billing_off_by_default.py` locks the real gate.

Note: `api/payment_endpoints.py` and `api/x402_endpoints.py` are mounted **unconditionally** in
`api/app.py` (no `if enable_credit_system` / `if x402_enabled` guard around `include_router`) —
each endpoint self-checks at request time (e.g. `container.get_service('balance_manager')` is
`None` when `ENABLE_AUTH` is off, and the handler 503s or falls back to an admin-only stub) rather
than being absent from the route table. The effective "no billing" guarantee is that **no billing
service is ever registered on the container**, not that the routes 404.

Multitenant deployments (Posture 2 — today `WEBGATE_MULTITENANT=true` or `POLYROB_POSTURE=multitenant`,
resolved by `webview/webgate.py::posture()`/`is_multitenant()`) are the intended posture for turning
`ENABLE_AUTH`/`ENABLE_CREDIT_SYSTEM`/`X402_ENABLED` on. **Forward note for Workstream B:** `webgate.posture()`
does not currently enforce this — an operator could set `POLYROB_POSTURE=local` while also setting
`ENABLE_AUTH=true`/`X402_ENABLED=true`, and nothing today refuses that combination. Wiring `posture()`
to hard-guard against billing flags on a `local`/`own_ops` instance (fail loud, not silently ignore)
is out of scope for Workstream C and is tracked as a B follow-up, not re-litigated here.

## Web fetch (Tier-1 lightweight web reader)

The default web tool is `web_fetch` (stateless `fetch_url(url) -> markdown`, no browser/Chromium).
The Playwright `browser` tool is opt-in (`tool_ids=['browser']` or a browser-oriented toolset) and
requires the extra: `pip install '.[browser]' && python -m playwright install chromium`.

| Flag | Default | What it does | Code anchor |
|------|---------|--------------|-------------|
| `WEB_FETCH_ALLOW_PRIVATE_URLS` | OFF | When true, `web_fetch` skips SSRF validation (allows loopback/private/metadata targets). Single-user/local dev ONLY — never enable in multi-tenant prod. When false (default), every redirect hop is re-validated and the connection is pinned to the validated IP (`tools/web_fetch/fetcher.py::safe_fetch`). | `tools/web_fetch/tool.py::_allow_private_urls` |

The web reader requests uncompressed responses and disables transport-level
automatic decompression. Servers that ignore `Accept-Encoding: identity` are
refused before their body is read. The default 10 MiB byte limit is enforced
before extending the response buffer, and one 15-second deadline covers DNS
validation plus every redirect. A timed-out blocking DNS lookup may continue in
its executor thread, but cannot start a subsequent connection for that fetch.

## `polyrob update` — self-update & rollback

The self-update mechanism (`cli/update/`, command `cli/commands/update.py`). "Latest" is
discovered from GitHub Releases (git/editable/systemd installs) or PyPI (pip/pipx). Snapshots
land under `<data_home>/snapshots` and capture every SQLite DB (config-resolved `bot.db` +
sidecars), `.env`/config, `identity/`, and `skills/`.

| Env | Default | Meaning | Code anchor |
|-----|---------|---------|-------------|
| `POLYROB_UPDATE_REPO` | derived from the dist Project-URL, else `theselfruleorg/polyrob` | GitHub `owner/name` the update-checker queries. Override for a fork / private mirror / renamed repo. | `cli/update/versions.py::resolve_repo` |
| `POLYROB_UPDATE_PYPI` | `polyrob` | PyPI project name for pip/pipx installs. | `cli/update/versions.py::resolve_pypi_package` |

Flags on the command (not env): `--check` (exit 0 up-to-date / 10 update-available /
1 unknown or source error), `--dry-run`,
`--channel stable|pre|git`, `--list-snapshots`, `--rollback [--snapshot NAME]`, `--json`, and
**`--force`** (override the in-use guard on `--rollback`). The rollback guard refuses while a
POLYROB **server/agent process is running** or a DB is actively write-locked
(`cli/update/process_guard.py`) — on a server, **stop the service before rolling back** (the
printed manual steps do this), or pass `--force`.

**Versioning policy (releases):** versions are **3-segment semver** `MAJOR.MINOR.PATCH`, tagged
`vX.Y.Z`. Bug-fix-only releases bump PATCH (`0.4.2` → `0.4.3`); new backwards-compatible features
bump MINOR (`→ 0.5.0`); breaking changes bump MAJOR. **Do not use 4-segment versions** (e.g.
`0.4.2.1`): the semver parser (`cli/update/versions.py::_SEMVER_RE`) reads the 4th segment as a
suffix and treats `0.4.2.1` as **equal to** `0.4.2`, so `--check` would never offer the update.
`release.yml` fails a tag whose `vX.Y.Z` ≠ `pyproject.toml` version.

### Custody and spend-storage invariants

`POLYROB_LOCAL` does not permit unsandboxed code execution when
`AGENT_WALLET_ENABLED` is on or any supported wallet seed is present:
`AGENT_WALLET_MASTER_SEED`, `PAYMENT_MASTER_SEED`, or legacy `MASTER_SEED`.
`run_code`/`run_tests` require a sandbox-capable `CODE_EXEC_BACKEND` in that
case; host Git, LSP diagnostics, and shadow snapshots refuse or skip execution.
These restrictions use existing flags (`core/security/host_execution.py`);
there is no custody bypass flag. MCP stdio also refuses in custody processes.
Installed extensions and signing keys still require separate operational isolation.

Wallet caps and amounts must be finite and nonnegative. `PolicyGate.reserve()`
holds a process-shared advisory lock for durable JSONL sinks across the check,
spend, and record sequence. Unreadable, corrupt, or truncated audit history blocks
further spending; the wallet factory never downgrades failed storage to an
in-memory ledger. Repair the ledger from trusted records before restarting.
The JSONL protocol is not atomic with chain settlement: a crash after broadcast
and before recording still requires reconciliation.

Token revocation reads fail closed when the denylist is unavailable. Repair its
path/permissions/database before restarting an instance latched unavailable;
do not delete the store to restore access. Failed logout writes latch the local
instance closed but cannot durably revoke a token in other processes. The generic
API authentication cache rechecks JWT expiry on every hit. All session decoders
require finite numeric `exp` and a nonempty `jti`; legacy tokens must sign in again.

### Terminal input and execution contracts

The persistent REPL accepts safe owner controls while a conversation is running;
other submissions remain in the editor. It shares context-reference preparation
with classic input and stores non-credential history in the profile's `history`
file. Interactive CLI approvals use the REPL input owner instead of a competing
stdin reader (`cli/ui/approval_prompt.py`, `core/approval_input.py`).

`polyrob run --output-format json|jsonl` implies noninteractive setup/approval input,
with diagnostics on stderr; `--no-input` selects that behavior for text runs too.
These are command options, not new environment flags. Session controls use
`control.sqlite3` within the session directory; pause/cancel acknowledge at a step
boundary (`core/session_control.py`). No money or approval gate is widened.

### Public-session and resource boundaries

Owner/SIWE JWTs require finite numeric `exp` and a nonempty `jti` on every HTTP
and Socket.IO decoder. Legacy tokens without these claims must sign in again.
Logout returns 503 if durable revocation fails; it retains the cookie so the
owner can retry rather than receiving a false success.

Session URLs confer no sharing authority. Both own_ops and multitenant require
the session owner for `/session/` and `/api/session/` reads. A scoped expiring
preview token remains valid only for that session's `/workspace/serve/` subtree.
MCP stdio connections refuse in custody processes; use a separately isolated
HTTP MCP service. Environment scrubbing alone is insufficient for same-UID code.

HTTP API and console request bodies are limited to 8 MiB, a 30-second total read
window, and 16 concurrent body reads per worker (`api/request_limits.py`).
Oversize bodies return 413, slow bodies 408, and saturated uploads 503. These
limits precede application parsers and include chunked bodies; document expansion
and WebSocket frames still require their own limits.

`CODE_EXEC_MAX_OUTPUT_BYTES` is enforced while reading command output, across
stdout and stderr together. Exceeding it terminates the command rather than
buffering unlimited output before truncating. Cancellation waits for host-child
cleanup; ephemeral Docker execution also requests container removal.

### Submission recovery and deployment safety

Solana sends persist the locally derived signature before RPC submission. x402
payment creation and Hyperliquid/Polymarket order submission persist attempt IDs
before the external operation. Unresolved submissions block further wallet
spending across restarts. A timeout, cancellation or negative merchant response
does not prove an authorization was unused. Reconcile against independent chain
or venue records; never delete the journal to unblock retries. Only a durable
policy audit charge releases an attempt automatically. x402 charges spend caps
at least the signed authorization amount, regardless of lower merchant claims.

EVM and deposit-treasury sends persist a `reserved` signing attempt before
calling the signer, then bind the locally derived hash before broadcast. A
signing or hash-binding error leaves the attempt unresolved. Venue attempts
require a durable charge for the same venue covering at least the prepared USD
amount; a smaller or unrelated charge cannot release them. This does not move
keys or SDK signing authority outside the agent interpreter.
EVM receipt polling requires the requested transaction hash and valid
status/block/gas fields. Unrelated or malformed replies remain pending rather
than being interpreted as a landed success or failure. Receipt inclusion alone
does not establish finality.

The submission database uses a shared advisory lock and a durable `.hwm` sidecar
containing its identity and minimum history-row count. Missing, replaced, empty,
or detectably truncated storage refuses spending. Intact legacy databases adopt
the sidecar on their first write. Preserve the database and marker together in
quiesced backups; never delete either to reopen spending. This single-host check
does not detect every historical state rollback or protect against an actor able
to rewrite all custody files. All wallet processes must run the new code together.

`python -m core.wallet.submission_recovery` produces read-only JSON evidence
for unresolved submissions using the configured RPC. EVM evidence checks chain,
sender, nonce, receipt/transaction identity, canonical block and the RPC's
finalized head. Solana evidence checks finalized status against the transaction,
fee payer, recent blockhash and slot. Missing or inconsistent evidence stays
unknown; unbound signing and venue attempts require operator evidence. Every
reservation remains held, even for a reported finalized success/failure. The
command neither signs nor books charges nor releases submissions. Exit codes
are 0 for no unresolved submissions, 1 when reservations remain, and 2 for
unreadable storage. Output contains public wallet/transaction identifiers and
belongs in private operational records. An empty report does not certify audit
health, wallet security or absence of transactions outside these rails.

Reported EVM fees cover execution gas only, excluding chain-specific L1/blob
charges; Solana transaction fees exclude transfers and rent. Reconciliation must
still establish complete effects and accounting. Configured RPCs are trusted
evidence sources, not independent proofs or a replacement for venue recovery.
Shared urllib EVM/Solana RPC reads request identity encoding, reject compression,
and cap raw replies at 8 MiB before JSON parsing. Incremental reads check a total
deadline alongside socket timeouts; system DNS/connect and other SDK transports
are outside a hard process-level deadline.

x402 quote, probe and paying transports cap raw response bytes before HTTPX or
SDK buffering, request identity encoding and refuse compressed responses before
decoding. The 2 MiB body cap retains settlement headers and marks truncation, so
an oversized body cannot suppress the payment audit. DNS validation and response
reads have deadlines; the SDK payment request/retry exchange has a total
30-second budget. Ambiguous failures retain their durable submission interlock.

### Chromium launch boundary

Local Playwright Chromium launches explicitly enable Chromium sandboxing; the
SDK default does not. `BrowserConfig.use_no_sandbox` is allowed only with explicit
`POLYROB_LOCAL=true` and no custody flag/seed. Sandbox-disabling extra arguments
cannot silently override the default. Custody processes refuse both fresh local
Chromium launches and the existing-local-Chrome attachment helper; configure a
separately isolated remote CDP/Playwright browser instead. An endpoint setting is
not proof of isolation: separate its UID/host, credentials and network access.
Remote endpoint URLs and connection errors are not logged verbatim because they
may contain authentication tokens. The Playwright driver remains trusted host
code; these launch guards do not create an independent signer boundary.

`core/security/browser_rail.py` is the ONE answer to "can this process drive a
browser, and through what": `none (custody)` with the install remedy,
`configured, unreachable (<reason class>)` with the service remedy, `remote cdp
ok (<version>)`, or `local Chromium`. The launch refusal, the step loop (which
skips the per-step page observation and warns once when the rail is down), the
`<tool-catalog>` (`gated:custody-no-browser` on `browser`/`x_browser`/
`dapp_browser`), the status snapshot's `identity` section (`browser:` line, WARN
only when a configured endpoint fails) and `polyrob doctor` all read it. The
snapshot never probes a non-loopback endpoint. `polyrob browser install` sets up
the same-host service as a boundary: a dedicated UID, the Chromium sandbox ON
through an AppArmor `userns` profile (never `--no-sandbox`), and a UID-keyed nft
egress chain (no loopback / RFC1918 / link-local / metadata from the browser).
Owner-ceremony launches (`x-account capture-session`/`signup`, the pfp still)
consult the same policy; `tests/test_browser_launch_ratchet.py` pins the launch
sites.

### Treasury sweep submission safety

The separately enabled deposit sweeper pins the configured chain and requires
the derived account, stored deposit address and source address to agree. It
reserves before signing and binds the transaction's locally computed hash in the
durable wallet submission journal before network submission, requires a matching successful receipt, then
records the sweep before releasing the reservation. Lost replies, cancellation,
failed receipts and bookkeeping failures retain the reservation and block fresh
wallet submissions until operator reconciliation. This deliberately shares the
wallet-wide interlock; an ambiguous deposit sweep can pause agent spending too.
Do not clear it based only on an RPC timeout. Native sweeps reserve the same
increased gas price they sign. Receipt inclusion is not a finality guarantee;
chain reorg handling and automatic reconciliation remain open.


### Ingestion snapshots and retained request bodies

Knowledge ingestion applies `KB_MAX_BYTES` to actual snapshot bytes, hashes and
extracts the same snapshot, and opens files through POSIX directory descriptors
without following symlinks. Non-regular files and hard-linked aliases are refused.
Platforms without descriptor-relative no-follow access refuse these reads.
Binary sniffing reads at most 4096 bytes instead of reading an entire file.
Directory discovery bounds its retained inventory to 20,000 paths and 4 MiB of
path/output bytes. The `rg` subprocess has a five-second deadline; its NUL-delimited
records preserve newlines in filenames. The fallback streams `scandir`, counts
directories as well as files, limits depth to 64 and checks a five-second deadline.
An unhealthy filesystem can still block an individual filesystem syscall.
Budget exhaustion is reported as `inventory_limited`; it never restarts an
unbounded fallback scan. Discovery runs off the event loop, and rejected binary
snapshots consume the discovery read budget too. These are fixed implementation
limits in `tools/knowledge_inventory.py`, independent of the smaller `KB_MAX_FILES`
and `KB_MAX_BYTES` admission limits.

HTTP body capacity remains reserved while an accepted body waits in its spool.
The slot and spool are released after the final replay chunk or on handler exit,
including cancellation. A consumed body does not occupy a slot for the lifetime
of a streaming response. Declared lengths must match received bytes. Application
parser allocations after replay are outside this middleware's spool budget.


### DOCX archive admission limits

Knowledge ingestion validates the exact DOCX byte snapshot before python-docx
parses it. Fixed limits are 1024 ZIP parts, 32 MiB total expanded content, 8 MiB
per part, 100,000 XML nodes across all parts, XML depth 128, table spans of at
most 64, and 100,000 budgeted table cells/spans. Extracted text is limited to
2 MiB of characters. DTDs, entities, encrypted/unsupported compression, duplicate
part names and ambiguous paths are rejected. XML content types require canonical
.xml/.rels part names to prevent bypassing XML validation with another suffix.
These limits intentionally reject some large or nonstandard documents.

Rejected or empty replacement documents preserve the last successfully ingested
source. `registry.kb_replace_source` publishes all chunks and the source hash/count
in one SQLite transaction. Write failure rolls back to the prior source. Worker
cancellation may complete a whole transaction, but cannot expose partial chunks.
Providers without atomic replacement support refuse publication. Vector indexing
remains a derived best-effort cache; semantic recall requires an exact match to
current tenant/collection/source/chunk content, so stale cached rows are excluded.

### Document parser resource limits

KB PDF/DOCX parsing and filesystem PDF extraction run through
`tools/document_parser.py` in disposable Python subprocesses. There is no
in-process recovery or automatic OCR fallback. Each process receives only the
authorized byte snapshot over stdin, an empty environment and a temporary working
directory. Fixed limits: 25 MiB input, 2 MiB extracted characters, 256 PDF pages,
20 MiB combined stdout/stderr, 15 seconds elapsed time, 10 seconds CPU, and two
admitted workers per application process. Saturation refuses promptly; cancellation
awaits child cleanup. DOCX archive admission also executes in the worker.

On Linux, the worker installs a 512 MiB address-space limit before parsing; failure
to install required limits refuses extraction. macOS has CPU/time/I/O limits but
no claimed hard memory boundary. These workers retain the application's OS UID;
an empty environment does not prevent filesystem/proc access or network use after
a parser exploit. Separate identities, filesystem/network restrictions and Linux
staging tests remain deployment requirements. Other document/media/OCR paths,
provider spending and browser/email resources are outside these limits.


Wallet audit reservations are task-owned. Synchronous append attempts from an
unrelated task/thread during an active reservation raise instead of borrowing
its file lock. The owner can record and ordinary appends resume after release.

### Operator wallet authority

The process wallet belongs to the bound operator principal. Money-tool loading,
controller execution, queued approvals and spending guards require matching
owner/session/execution identity; an authenticated customer role is insufficient.
Wallet ledger, positions and book endpoints use the same owner boundary and
refuse arbitrary ledger selection. Direct trusted Python calls and SDK key
access remain outside an independent signer boundary.
